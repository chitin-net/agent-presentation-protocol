# Changelog

All notable changes to the Agent Presentation Protocol (APP) specification are recorded here.

## [0.5] — Draft (not yet released)

Drafted 2026-09-09, extended 2026-09-10. Not published. The exchanged `protocol_version` remains `"0.4"` everywhere in this repo until this revision is finalized and released — nothing in this entry is live on the wire yet.

This is a minor, fully backward-compatible revision: every addition below is optional, and §10.2 requires implementations to silently ignore unknown fields and message types.

### Added

- `chat_stream_chunk.directives` — an optional presentation-directive track (expression, pacing, gesture, gaze) keyed to a character offset in `accumulated`, carried as an additional field rather than a sibling message type. See SPEC.md §4.2.1.
- `agent_notification_response.decision` — an optional structured `{action: allow|deny, scope: once|session|always}` field for approval-shaped notifications, gated by the new `capabilities.initiation.supports_decision` Agent Card flag. An agent that does not see the flag MUST fall back to the existing free-text `user_response` / `chosen_option` path. See SPEC.md §4.13.
- Attention-arbitration vocabulary, layered additively on top of `presence_update` (§12) without changing its semantics: the `presence_roster` message type (multi-surface visibility), an optional `priority` field on `presence_state.json` plus a recency fallback (tie-break rule), and the `attention_floor` message type (floor/yield signaling), gated by the `capabilities.supports_presence_roster` and `capabilities.initiation.respects_attention_floor` Agent Card flags. See SPEC.md §15.
- Surface-to-agent file upload: a genuinely new message-type family, not a reinterpretation of `artifact_create`/`artifact_update`/`artifact_request` (§4.11), which carry no upload direction at all. `file_upload` (Surface → Agent or Relay) delivers a file under a declared, revocable `scope` (`usage`: `process`/`retain`; `duration`: `single_use`/`session`/`ttl`, no indefinite grant), inline or by reference (or both) depending on declared size limits; `file_upload_response` (Agent → Surface, relay-routed) gives every upload an explicit accept/reject so none can fail silently; `file_scope_revoke` (Surface → Agent or Relay) revokes a grant early. Gated by the new `capabilities.supports_file_upload` Agent Card flag (with accompanying `capabilities.file_upload` size/type limits) — a surface MUST NOT send `file_upload` to an agent that hasn't declared it. Manifest-versus-payload routing for `content_ref` is deliberately left open; both routing choices satisfy the schema unchanged. See SPEC.md §16.
- `surface_agent_card` (Relay → Agent) and `surface_agent_card_removed` (Relay → Agent): specifies the wire shape of "the relay forwards a surface's card to the agent," already implied by §3.1/§3.3/§6 but never previously given a message shape, so §6's "Agent adapts to surface's card" table was previously unimplementable. Kept as a distinct type from `agent_card` (which a bridge itself sends upward) so an inbound forwarded card can never be mistaken for an echo of the bridge's own card. A bridge that connects after surfaces are already online is replayed each known surface's card using the same shape, rather than a separate roster type. See SPEC.md §17.
- Relay-assigned surface identifier: `surfaceId` (and, when (re)minted, `surfaceToken`) on the `connected` system event (§4.3), which `surface_agent_card`, `surface_agent_card_removed`, and `agent_notification_late_response` (below) all reference to name which surface they concern. Deliberately distinct from the self-declared, unverified `source_surface_id` (§12.3) used by `presence_update`/`presence_roster` — neither substitutes for the other. Specifies only the wire contract (an opaque id, an opaque reissuable token, and the reissuance rule); the minting mechanism is an implementation choice. See SPEC.md §18.1.
- `presence_roster`'s per-surface entries gain an optional `surface_id` field carrying the relay-assigned identifier from §18.1, alongside the untouched, self-declared `source_surface_id` — not a replacement for it. Present only when the relay can supply one for that entry. Lets an agent attribute a capability or card to the surface a roster entry describes using the identifier that is actually stable across reconnects, while `source_surface_id` remains the routing key other messages (e.g. `attention_floor.target_surface_id`) use. Also resolves the "does not define a wire message for exposing that correlation" language in §18.1, which this addition supersedes. See SPEC.md §15.1 and §18.1.
- `agent_notification_already_resolved` (Relay → Surface): a new, distinct message type telling a late-answering surface that the `agent_notification` it just answered was already resolved by another surface's answer or by ring timeout. Kept separate from `agent_notification_response` — which remains cleanly Surface → Relay → Bridge/Desktop only — for the same reason `surface_agent_card` (§17.1) is distinct from `agent_card`: reusing a message type across both directions would make an inbound relay-originated message indistinguishable from an echo of the surface's own outbound answer. Paired with `agent_notification_late_response` (Relay → Bridge/Desktop), which reports both surfaces and both results to the agent side rather than silently discarding the late answer. See SPEC.md §4.13 "Late answers."
- `agent_initiated_message_response` (Relay → Bridge/Desktop), `result: "unavailable"`: establishes a response contract for `agent_initiated_message`, which previously had none at all — an agent could not tell "delivered" from "reached nobody" when zero surfaces were connected. Mirrors the `unavailable` result `agent_notification` already had. See SPEC.md §4.13.
- `agent_activity` (Agent (Bridge/Desktop) → Relay → Surface): a new message type for an agent's own working state — "I have begun a unit of work," "that work is now finished/failed/cancelled/expired" — resolving a deferral that deliberately shipped nothing rather than guess at the contract. Not an extension of `presence` (§4.10, routing-less and contract-less) and not a repurposing of `presence_update` (§12, surface-emitted, describes the user's state, not the agent's own work — reusing it would repeat the `source_surface_id`/`surfaceId` conflation §18 already had to correct). `event: "start" | "progress" | "clear"`, correlated by an agent-assigned `task_id` (with optional `reply_to` back to the originating `chat_message` when the work is turn-scoped) so a surface can hold several concurrent indicators without confusing them. The clear-on-finish contract is layered three ways so a stranded indicator cannot happen by a single point of failure: the agent MUST clear every `start` on completion/failure/cancellation/expiry and MUST re-clear on reconnect; the relay MUST track outstanding `task_id`s per bridge connection and synthesize a `clear` (`reason: "expired"`) if that bridge disconnects and does not return within the same 60-second grace window §12.5 already uses; and `start` MAY carry an optional `ttl_seconds` self-expiry floor a surface MUST honor locally, independent of both agent and relay, for the case where the agent hangs without dropping its connection. `agent_activity` is never cached alongside PresenceState and never sent on `/ws/ambient`. Gated by the new `capabilities.supports_agent_activity` Agent Card flag (surface-side, distinct from `supports_presence`) — an agent SHOULD NOT emit into a surface that hasn't declared it. See SPEC.md §19.
- `agent_activity` `event: "progress"` (§19.2.1): a third event on the same message type, added so a task that runs for minutes doesn't read as one static indicator — indistinguishable from the unresponsiveness the whole feature exists to rule out — for the entire wait between `start` and `clear`. Carries only an updated `label` for work already announced, correlated by the same `task_id`; no new speech, no `kind`/`reply_to`/`reason` (meaningless in this position), and no new capability flag — gated by the existing `capabilities.supports_agent_activity`, since a surface that silently ignores an unrecognized `event` value is already correct in its presence. A `progress` for a `task_id` neither a relay nor a surface currently has outstanding MUST be ignored without creating any tracking state (relay: never mutates the outstanding-`task_id` registry off a `progress`; surface: never treats an unmatched `progress` as an implicit `start`) — the registry that drives §19.4.2's disconnect fallback is populated and depopulated by `start`/`clear` alone. The agent is responsible for rate-limiting its own `progress` emission per `task_id` (recommended: no faster than roughly 1/second in ordinary operation) — an unbounded stream is a real denial-of-service shape against a surface. `progress`-following-`progress` for an already-known `task_id` is the one narrow exemption from §19.5's "no coalescing or dropping" rule: since each supersedes the last, a relay MAY drop a stale one in favor of a newer one, but MUST NOT reorder or coalesce a `clear` around a `progress`, and the exemption never extends to `start` or `clear` themselves. `progress` explicitly resets a surface's local `ttl_seconds` floor on receipt (deliberate: it is stronger evidence of life than a repeated `start`), but has zero effect on the relay's connection-keyed disconnect grace window (§19.4.2) — the two are independent by design, as they already were for `start`. See SPEC.md §19.2.1.

### Corrected

- §7.1 stated that a bridge pairing token "is bound to a specific (agent, surface) pairing at issuance." This was untrue of the reference relay (and in tension with this spec's own multi-surface, multi-agent model, §4.12/§15): the token binds an agent to a user's account, not to a specific surface, and a surface's own credential is likewise account-scoped rather than agent-scoped. Corrected to describe account-based matching instead of a fixed pairwise binding; see SPEC.md §7.1 and §18.1.

### Noted

- §16 gains an implementation-status note: no implementation of Surface-to-Agent File Upload exists anywhere yet — not the reference relay, not the reference bridge, not any reference surface. No normative or wire content changed. See SPEC.md §16.
- §15.3 gains an implementation-status note: the reference relay does not yet implement targeted `attention_floor` delivery — its current surface-routing path does not resolve `target_surface_id` and would broadcast the directive to every connected surface instead of the one addressed. No normative or wire content changed. See SPEC.md §15.3.
