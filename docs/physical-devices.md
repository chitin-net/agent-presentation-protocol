# Physical Devices: Robotics, IoT, and Industrial Integration

The Agent Presentation Protocol (APP) extends beyond screens to physical devices — humanoid robots, vehicles, industrial machines, agricultural equipment, and consumer appliances. This document explains the protocol's physical device capabilities, the envelope principle, and how to integrate any machine with a conversational interface.

## The Core Idea

Every machine that humans interact with could benefit from a conversational interface. But most machines shouldn't have screens bolted onto them — a combine harvester, a warehouse AGV, a vacuum robot, a CNC machine. They do physical work. Humans interact with them infrequently and from a distance.

APP lets any machine become conversationally accessible through surfaces the user already carries — their phone, a kiosk, CarPlay, a desktop. The machine publishes its state and available actions; humans talk to it naturally; structured commands flow back.

## The Envelope Principle

APP defines the **message envelope** (JSON structure, required fields, timing semantics, safety constraints). The **device designer** fills in the **vocabulary** (what commands exist, what parameters they take, what sensors report).

This is the same relationship HTTP has to your API. HTTP defines GET, POST, headers, status codes. It doesn't define what your endpoints do. APP for physical devices works the same way.

**What this means practically:** a robotics company integrates by reading the spec, declaring their device's commands and sensors in an Agent Card, and writing a thin adapter. They bring domain expertise about what their machine does; the protocol provides transport, surface conventions, relay intelligence, and the human interaction layer.

## Three Device Tiers

### Tier 1: Screen-Based Surfaces

iPads, monitors, kiosks running any APP avatar surface. No physical actuation. Uses `chat_message`, `chat_stream_chunk`, `chat_stream_end` — no motor commands needed.

### Tier 2: Smart Devices (interaction_model: "standard")

Devices with onboard AI that project to APP surfaces. Electric vehicles, humanoid robots with GPUs, smart home hubs running local agents. The device connects as an agent, handles natural language locally, and uses APP surfaces as additional interaction points.

**Key protocol features used:**
- Agent Card with `device` metadata (type, status, available_actions)
- `sensor_event` messages for real-time status (battery, location, task progress)
- `motor_command` for physical directives when surfaces control the device
- Standard `chat_message` / `chat_stream_chunk` for conversation

### Tier 3: Headless Devices (interaction_model: "headless")

Machines with no screen, no speaker, no AI. The device publishes state and available actions through a thin adapter. The relay-side intelligence layer handles natural language interpretation and maps user requests to structured `device_action` commands.

**Key protocol features used:**
- Agent Card with `interaction_model: "headless"` flag
- `sensor_event` for state reporting
- `device_action` for structured commands (generated by relay intelligence, not by the device)
- No `chat_stream_chunk` — the device doesn't generate text responses

## Motor Command Reference

Motor commands are the protocol's mechanism for physical directives. They follow the envelope principle — the protocol defines the structure; the device defines the vocabulary.

### Envelope

```json
{
  "type": "motor_command",
  "id": "uuid-v4",
  "command": "string (device-defined)",
  "parameters": { },
  "timing": {
    "mode": "immediate | queued | synchronized",
    "delay_ms": 0,
    "sync_to": "message-uuid | null"
  },
  "safety": {
    "requires_confirmation": false,
    "timeout_ms": 30000,
    "abort_on_error": true
  },
  "reply_to": "session-uuid",
  "timestamp": 1774648679638
}
```

### Timing Modes

**Immediate** (default): Execute now. Used for single commands triggered by user request.

**Queued**: Add to the device's command queue and execute in order. Used for multi-step sequences ("go to the lobby, then turn left, then stop at room 105").

**Synchronized**: Execute in sync with a chat message referenced by `sync_to`. Used for coordinated speech-and-movement:

```
[gesture:wave] Welcome to the Hilton! [move:approach]
I see you have luggage. [gesture:point_elevator]
The elevators are right this way. [move:lead_to_elevator]
```

The surface parses inline tags, generates motor_command messages with `timing.mode: "synchronized"`, and coordinates physical execution with TTS playback.

### Safety Object

Safety-critical commands (moving a forklift, unlocking a door, starting heavy machinery) should declare `requires_confirmation: true` in the Agent Card's action definition. When the relay or agent sends such a command, the surface prompts the user before forwarding to the device.

`timeout_ms` defines how long to wait for completion confirmation. `abort_on_error` determines whether queued commands halt if one fails.

## Sensor Event Reference

Sensor events carry data from physical devices to agents and surfaces.

### Envelope

```json
{
  "type": "sensor_event",
  "id": "uuid-v4",
  "sensor": "string (device-defined)",
  "value": { },
  "trigger": "periodic | threshold | event",
  "device_timestamp": 1774648679000,
  "timestamp": 1774648679638
}
```

### Trigger Modes

**Periodic**: Sent at regular intervals defined by the device. Battery level every 60 seconds, GPS every 5 seconds, harvest progress every 30 seconds. Surfaces use periodic events for real-time dashboards.

**Threshold**: Sent when a value crosses a boundary. Battery below 20%, temperature above safe limit, bin full. Used for alerts that need attention without constant polling.

**Event**: Sent when a discrete thing happens. Task completed, error occurred, person detected, zone entered. One-shot notifications.

### Examples

```json
// Combine harvester — periodic progress
{ "sensor": "harvest_progress", "value": { "field": "north_40", "percent_complete": 73, "yield_bushels_per_acre": 185 }, "trigger": "periodic" }

// Warehouse AGV — threshold alert
{ "sensor": "proximity_alert", "value": { "direction": "forward", "distance_m": 1.2, "object_type": "person" }, "trigger": "threshold" }

// Robot vacuum — event notification  
{ "sensor": "zone_complete", "value": { "zone": "kitchen", "duration_minutes": 12, "next_zone": "hallway" }, "trigger": "event" }

// CNC machine — threshold warning
{ "sensor": "tool_wear", "value": { "tool": "insert_3", "wear_percent": 89, "estimated_parts_remaining": 4 }, "trigger": "threshold" }
```

## Device Action Reference

Device actions are structured commands for headless devices, generated by the relay-side intelligence layer from natural language.

### Envelope

```json
{
  "type": "device_action",
  "id": "uuid-v4",
  "action": "string (matches available_actions)",
  "parameters": { },
  "source_message": "chat-message-uuid",
  "timestamp": 1774648679638
}
```

The `action` field MUST match an entry in the device's Agent Card `available_actions`. The relay validates this before forwarding. The `source_message` provides an audit trail linking the action to the user's original request.

### Available Actions Schema

Actions are declared in the Agent Card with typed parameters:

```json
"available_actions": [
  {
    "id": "clean_room",
    "name": "Clean specific room",
    "params": [
      {
        "name": "room",
        "type": "string",
        "options": ["living_room", "kitchen", "bedroom", "office"]
      }
    ]
  },
  {
    "id": "set_speed",
    "name": "Set ground speed",
    "params": [
      { "name": "mph", "type": "number" }
    ]
  },
  {
    "id": "emergency_stop",
    "name": "Emergency stop all movement",
    "params": [],
    "safety": { "requires_confirmation": true }
  }
]
```

Parameter types: `string`, `number`, `integer`, `boolean`, `array`. String params can include `options` arrays to constrain valid values. The relay intelligence uses these constraints when mapping natural language to actions — it won't generate a room name that isn't in the options list.

## The Surface Continuum

Physical surfaces are a spectrum from stationary screens to full humanoid embodiment:

| Stage | Example | Motor Commands | Display |
|-------|---------|---------------|---------|
| 1. Stationary screen | iPad kiosk | None | VRM avatar |
| 2. Motorized display | Screen on pan/tilt mount | pan, tilt, height | VRM avatar |
| 3. Mobile screen robot | Tablet on wheeled base | go_to, follow, dock | VRM avatar |
| 4. Humanoid with display | Robot with screen face | walk, gesture + screen | VRM avatar + physical gesture |
| 5. Full humanoid | Robot, no screen | walk, gesture, express | Physical expression only |

An agent built for Stage 1 works at Stage 5. Each stage adds capabilities to the Agent Card; the agent and surface negotiate what they both support.

## Writing a Device Adapter

A headless device adapter is typically 30-80 lines of code:

1. **Read the device's native API** — HTTP, MQTT, serial, Modbus, whatever the machine speaks.
2. **Declare an Agent Card** — List the device's status fields, available actions with parameters, and sensor event types.
3. **Connect to the relay** — open a WebSocket to `/ws/bridge` and send the Agent Card as the first message (SPEC §3.3).
4. **Send sensor events** — Periodically read device state and send `sensor_event` messages.
5. **Handle device_action** — Receive structured commands and translate to native API calls.

The device manufacturer doesn't need to change anything. If the machine has any kind of API, you can write an adapter.
